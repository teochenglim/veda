# RELEASE v0.5.0 — Telemetry you can audit

**Status:** implemented (tests enforce the ACs below)
**Theme:** same counts, more signal — and you can see exactly what leaves your machine before it does.

## Release notes

### Added
- **`ext` block in telemetry payloads** (same single opt-in consent, counts
  and enums only):
  - `agent` + `clients`: which MCP integrations actually drive Veda
    (claude / cursor / codex / …), from the `clientInfo.name` the MCP client
    already sends at `initialize`.
  - Feature-adoption flags: `semantic_enabled`, `sync_enabled`.
  - `embed_provider` as a fixed enum (`ollama` / `lmstudio` / `openai` /
    `other`) — never the URL, never the key.
  - Pipeline quality: `gate_rejected` (turns the cheap gate dropped),
    `ui_opens` (review-UI adoption), `serve_minutes`, `db_size_kb`.
  - `errors`: `{code: count}` from an allowlist (`embed_fail`, `flush_fail`,
    `llm_fail`, `wal_fail`, `sync_fail`) — delivering the "counts, recall
    hit rate, error codes" promise made in the `veda init` first-run prompt.
- `veda telemetry preview` and `veda telemetry export` include the `ext`
  block, so the transparency guarantee covers the new fields too.
- Server side (telemetry worker v0.2, ships with this release from its own
  repo): whitelisted `ext` keys land in a `rollups.extra` column so they
  outlive the 90-day raw window. Older workers simply ignore `ext` (unknown
  field), so the client can ship first.

### Never sent (enforced by test)
URLs, hosts, file paths, locale/timezone/language, free-form text, content
hashes — nothing derived from memory content, ever.

## Acceptance criteria

| # | Acceptance criterion | Test |
|---|---|---|
| AC1 | A consented install's payload carries the `ext` block with the new fields; without collector data the payload stays v0.4-shaped (ext omitted) | `telemetry.TestAC1_ExtBlockPresentOnlyWithData` |
| AC2 | The serialized payload contains no URL/path/locale patterns; the embedding endpoint never appears | `telemetry.TestAC2_ExtNeverContainsUrlsOrPaths` |
| AC3 | Sanitization: agent/client names lowercased `[a-z0-9._-]` and ≤ 32, unknown → `other`, maps capped (clients ≤ 8, errors ≤ 16, allowlist only) | `telemetry.TestAC3_ExtSanitizedAndCapped` |
| AC4 | Erasure unchanged: `veda telemetry forget` is still one unauthenticated `DELETE /?install_id=`; `ext` rides the same install id | `telemetry.TestAC4_ForgetUnchangedWithExt` (+ existing `TestAC9_DeleteErasure`) |

Supporting tests: absent-`ext` back-compat (a payload with no collector
data is byte-identical to v0.4's shape).

## Server contract

Unchanged in shape: `POST /` ingest, `DELETE /?install_id=` erasure, exactly
as [prd.cloudflare.md](../prd.cloudflare.md). `ext` is an unknown field to
worker v0.1 (ignored, stored verbatim in the 90-day raw window) and a
whitelisted block to worker v0.2 (rolled up long-term). The persisted column
set only grows alongside this client release, per PRD §3.

## Design

Sanitization lives in one place (`internal/telemetry/ext.go`): the only way
a string enters `ext` is through `sanitizeName`, `sanitizeErrorCode`, or the
`ProviderFromURL` enum — there is no API to set free text. See
[DESIGN/07](../DESIGN/07_design_telemetry_and_privacy.md).
